# 7/1/26 Plan — Usability Polish + Demo-Data & Marketing Prep

**Branch:** work on `feat/showcase-prep` (off `Dev-Latest`); PR → `main` only when verified.
**Goal:** Make the app feel finished for a first-time visitor (Part 1), and make it look *alive* — full of activity — for screenshots and social posts (Part 2).
**Constraints:**
- GeoDjango needs Docker to run/test locally (no GDAL on host). Verify everything in `docker compose run --rm web python manage.py …` before merging.
- 🏠 **Demo data is LOCAL ONLY.** `seed_demo` runs against the local Docker Postgres/PostGIS dev DB on `localhost` — for building/screenshotting the UI. No demo hosting, no subdomain, no cloud DB.
- 🚫 **Never seed or mutate the production database.** The prod DB carries only real user activity. The `seed_demo` command hard-refuses to run against prod (see P2.1 safety rails).

---

## Guiding principle

The single biggest marketing lever isn't a new feature — it's **an app that looks used**. An empty map kills trust. So Part 2 (demo data) is what makes Part 1 (UI/UX) actually *photograph* well. Do the seed command first-ish so every UI change is evaluated against realistic content, not an empty state.

## Part 1 — Usability (UI/UX)

Ordered by impact-per-hour. Each item is scoped to the existing vanilla-JS + Leaflet + Django-template stack (no framework, no build step).

### P1.1 First-run clarity (highest impact)
- **Empty-state → guided state.** When `/api/features/` returns few/no sites in view, show a friendly overlay card ("Be the first to report litter here — click *Report Trash* to drop a pin") instead of a bare map.
- **1-time onboarding coachmarks.** A dismissible 3-step tooltip tour on first visit (localStorage flag): (1) switch modes, (2) drop a pin / draw an area, (3) filter by status. Keep it skippable and keyboard-accessible (reuse existing modal focus-trap from `utils.js`).
- **Mode affordance.** Make the Report/Cleanup switcher visually unmissable (larger, iconized, active-state color from `palette.css` tokens). New users don't currently know the app has two modes.

### P1.2 Trust & legibility
- **Marker clustering** at low zoom (leaflet.markercluster) so a full map reads as "lots of activity" rather than a blob. Directly boosts screenshot quality.
- **Status/severity legend** always visible (collapsible on mobile). A map with unexplained colored dots is noise.
- **Detail panel polish:** consistent before/after photo framing, relative timestamps ("2 days ago"), reporter/verifier attribution, hazard-type chips (the new `hazard_types` JSON field).
- **Loading & error states:** skeleton/spinner on feature fetch; the existing toast system (`utils.js`) for failures. No silent blank screens.

### P1.3 Mobile-first pass (most social traffic is mobile)
- Bottom-sheet control panel on small screens instead of a side panel.
- Larger tap targets (44px min), thumb-reachable primary actions.
- Verify the PWA install prompt + service worker still register cleanly; "Add to Home Screen" is itself a marketing surface.

### P1.4 Showcase pages (these are the ones you'll link in posts)
- **`/cleanups/`** — make it a proper before/after gallery (grid, lightbox, bag-count + district badges). This is your #1 shareable page.
- **`/challenges/`** and **`/districts/`** — leaderboard-style progress bars, district stats, "join the challenge" CTA.
- **`/embed/`** — confirm the embeddable map looks good in an iframe for partner sites / link previews.
- **Landing/hero:** a short value-prop header on `/` for first-time visitors (what this is, one CTA to sign up).

### P1.5 Sharing & link previews (small effort, big marketing payoff)
- **Open Graph / Twitter Card meta tags** on `/`, `/cleanups/`, each `/districts/<slug>/`, and each `/challenges/<slug>/` so links unfurl with a real image + title on social.
- Per-district and per-event **share buttons** (copy link / native share sheet).
- The `/api/events/<id>/flyer/` endpoint already exists — surface a "Download flyer" button on event pages for printable/postable promo.

### P1.6 Accessibility regression guard
- Keep WCAG AA: re-check contrast on any new tokens, ARIA on new modals/sheets, keyboard nav on coachmarks and lightbox. Don't let the polish break the a11y that's already there.

## Part 2 — Demo Data & Marketing Prep

### P2.1 New management command: `seed_demo`
Model the new command on the existing `geoapp/management/commands/seed_screenshot_demo.py` (same idempotent, `--reset`, `--json`, `@transaction.atomic` pattern), but scale it up to a *populated region*. Add `geoapp/management/commands/seed_demo.py`.

**Requires districts first:** run `seed_district` + `fetch_districts` so sites/events/teams can be spatially assigned. Generate all geometry **inside real district polygons** (sample random points within `District.geometry` bounds, keep ones that `covers`) so nothing lands in the ocean on the map.

**Volume targets (tune via `--scale` arg):**

| Entity | Count | Notes |
|---|---|---|
| Users + `Profile` | ~40 | Mix of `MEMBER`, a few `COORDINATOR`, 1–2 `ADMIN`; realistic usernames/display names; `public_profile=True` for leaderboard visibility |
| `Team` + `TeamMembership` | ~8 teams | Spread across `OrgType` (school, civic, church, scout); each with a leader + 3–6 members |
| `TrashSite` | ~120 | Spread across all 13 areas (Putnam + 12 districts); realistic mix of `PENDING`/`IN_PROGRESS`/`CLEANED`/a few `INVALID`; varied `severity`, some `hazard_flag`+`hazard_types`, a few `chronic_site`, some `area` polygons not just points |
| `CleanupProof` + `Photo` | ~60 | Attached to CLEANED sites; realistic `bags_count`; **before/after photos** (see P2.2) — this is what makes `/cleanups/` shine |
| `RouteCleanup` | ~15 | Roadside linestrings with `time_spent_minutes` |
| `CleanupEvent` + `EventRSVP` | ~12 events | Mix of past `COMPLETED` and upcoming `SCHEDULED`; 5–20 RSVPs each; some with `max_attendees` near full to show demand |
| `Challenge` | ~4 | One `ACTIVE` (mid-progress toward `bag_goal`), one `UPCOMING`, two `COMPLETED` |
| `Badge` + `UserBadge` | full badge set | Award badges to top users so profiles/leaderboard look earned |
| `ActivityLog` | derived | Log activity for every report/clean/route so the activity feed is full |
| `FeedbackEntry` | ~10 | Mix of types/statuses so the admin/coordinator view isn't empty |

**Backdate everything.** Reuse the `seed_screenshot_demo` trick of `.update(created_at=...)` after creation to spread records across the last ~90 days. A realistic *timeline* (steady reports + cleanups over months) is what sells "active community" in stats/leaderboard/heatmap. Cluster some activity into "event days" so the heatmap and monthly digest have shape.

**Safety rails:**
- Namespace all demo users (e.g. username prefix `demo_`) and tag records so `--reset` can cleanly delete only demo content — never touch real user data.
- Guard against prod: refuse to run if `DEBUG=False` unless `--force` is passed, so you can't accidentally seed the live DB.
- Idempotent via `get_or_create` / deterministic slugs.

### P2.2 Demo media (the make-or-break for screenshots)
- Ship a small set of **royalty-free before/after litter photos** in `geoapp/management/demo_assets/` (or a fixtures dir); attach them as `Photo` records (REPORT/BEFORE/AFTER) so galleries and detail panels have real imagery.
- In prod-like demo, these upload to R2 like any photo; locally they use `MEDIA_ROOT`. Keep the set tiny (a dozen reused images) to avoid bloating the repo — consider `git lfs` or a download step if size is a concern.

### P2.3 Where the demo data lives (DECIDED — local only)
No demo hosting. `seed_demo` populates the **local Docker dev database** and you view it at `http://localhost:8000`. That local instance is where you'll:
- build and screenshot/record the UI against a full-looking map,
- capture the marketing assets (P2.4) from a browser or the Playwright pipeline.

Workflow:
```powershell
docker compose up -d db web
docker compose run --rm web python manage.py seed_district
docker compose run --rm web python manage.py fetch_districts
docker compose run --rm web python manage.py seed_demo            # populate
docker compose run --rm web python manage.py seed_demo --reset    # wipe demo data & re-seed
```
- Local media (photos) go to `MEDIA_ROOT` on the mounted volume — no R2 needed for the demo.
- The prod deployment is untouched: it never runs `seed_demo`, and the command refuses to run when `DEBUG=False` anyway (P2.1). Marketing assets are produced *from* this local instance, not from a hosted demo.

### P2.4 Marketing asset generation
- **Screenshots/screen-recordings:** extend the existing Playwright `e2e/` + `seed_screenshot_demo` pipeline to capture the *populated* views (full map, `/cleanups/` gallery, a challenge leaderboard, an event page, mobile bottom-sheet) at social-ready resolutions. Automate so assets regenerate as the UI changes.
- **OG image:** a branded 1200×630 share image (logo + tagline + map snapshot) referenced by the P1.5 meta tags.
- **Content kit:** a `marketing/` folder with (a) 8–10 draft post captions (launch, before/after spotlight, "join a challenge", district call-to-action, volunteer shoutout), (b) hashtag list, (c) the flyer PNG from `/api/events/<id>/flyer/`. Draft copy, you approve/edit.
- **Analytics before launch:** add lightweight, privacy-respecting analytics (e.g. Plausible/Umami) so you can measure which posts drive signups. One `<script>` + settings toggle.

### P2.5 Pre-launch hygiene
- Confirm email backend is real (SMTP env vars, not console) so RSVP confirmations / reminders actually send during a campaign — `send_event_reminders`, `send_monthly_digest`, `send_monthly_report` already exist.
- Rate limits + IP-ban middleware stay on (a public campaign = bots will find it).
- `robots.txt` / sitemap for the public showcase pages so they're indexable.

## Sequencing (efficient path)

1. **`seed_demo` command + demo media** (P2.1–P2.2) — everything else is judged against real content.
2. **First-run + trust UI** (P1.1–P1.2) — biggest first-impression wins, now visible against seeded data.
3. **Showcase pages + sharing/OG tags** (P1.4–P1.5) — the actual links you'll post.
4. **Mobile pass** (P1.3).
5. **Demo environment + marketing assets + hygiene** (P2.3–P2.5) — package and ship.
6. **a11y regression sweep** (P1.6) throughout, verified at the end.

Each step: implement → `docker compose run --rm web python manage.py test` (+ targeted new tests for `seed_demo`) → visual check → commit. PR to `main` only after the full suite passes.
